## 0. فريق العمل المقترح لإغلاق الجاهزية

لتكوين «فريق العمل بالكامل» وتشغيل المنصة بثقة، الأدوار التالية مطلوبة (RACI مختصر):

| الدور                       | المسؤولية الأساسية                                         | أول مخرجات                                      |
| --------------------------- | ---------------------------------------------------------- | ----------------------------------------------- |
| **مالك المنتج / الإدارة**   | قرار سياسة الحجز (عضو فقط vs ضيف)، اعتماد المحتوى والأسماء | قرار BMC/lookup؛ أسماء قيادات إن رُغبت علنًا    |
| **مسؤول المحتوى الطبي**     | تنظيف DEMO/E2E، صور الأطباء، أوصاف التخصصات/الفروع         | قائمة أطباء إنتاج نظيفة على `/team` و`/doctors` |
| **مهندس منصة (Full-stack)** | إصلاح الحجز، slug→UUID، مراجع BMC، ربط `patient_id`        | حجز يعمل من البحث حتى التأكيد                   |
| **مهندس بيانات / Supabase** | service-role صحيح، RPC عامة، RLS، revoke anon              | availability حقيقية؛ أمان create                |
| **مهندس DevOps / أسرار**    | GitHub secrets، Twilio، OTP pepper، hCaptcha               | OTP واتساب حي؛ CI لا يتخطى RLS بصمت             |
| **مصمم واجهة / هوية**       | توحيد قالب الرئيسية (PR #13)، إزالة مكوّنات ميتة           | هيرو بصورة + شريط حجز متسق                      |
| **ضمان جودة (QA/E2E)**      | تحديث اختبارات الضيف → جلسة مريض                           | suite أخضر بعد فرض التسجيل                      |
| **أمن / امتثال**            | مراجعة EXECUTE لـ anon، SECDEF، سجلات التدقيق              | لا تجاوز لبوابة HTTP                            |

> صفحة الموقع `/team` تعرض الفريق الطبي من قاعدة البيانات + أدوار الإدارة (بدون أسماء شخصية علنًا للخصوصية). الصفحات الفرعية `/team/about` و`/team/leadership` أُكمِلت في هذا الفرع كمحتوى حقيقي بدل stubs الاختبار.

## 1. ملخص تنفيذي

| المحور                 | الحالة | ملاحظة                                                          |
| ---------------------- | ------ | --------------------------------------------------------------- |
| الصفحات العامة         | ✅     | معظم المسارات تُحمَّل                                           |
| الهوية RTL             | ✅     | باعشن / تيل-ذهبي                                                |
| فريق العمل `/team`     | ⚠️     | أطباء من DB (يشمل اختبار) + قيادة بأدوار فقط؛ فرعيات كانت stubs |
| الحجز بعد التسجيل      | ⚠️     | بوابة `/book` موجودة؛ إنشاء الموعد يعتمد service-role + OTP     |
| بيانات الإنتاج الظاهرة | ❌     | فرع E2E + أطباء DEMO ظاهرة للجمهور                              |
| مواعيد availability    | ❌     | مفتاح خدمة غير صالح → أوقات فارغة                               |
| تتبع/إلغاء بمراجع BMC  | ❌     | lookup/track ما زالا أقرب لعقد BAA                              |
| CI / أسرار             | ⚠️     | بوابات جزئية؛ RLS يتخطى على PR بدون أسرار                       |
| قالب الرئيسية الجديد   | ⏳     | مسودة PR #13 غير مدمجة في `bashen` بعد                          |

**أهم 3 إجراءات فورية**

1. تصحيح `SUPABASE_SERVICE_ROLE_KEY` (رفض أي مفتاح `sb_publishable_`).
2. إخفاء DEMO/E2E من RPC العامة (`list_public_*`).
3. دعم مراجع `BMC-…` في `/lookup` و`/track`/`cancel` + توحيد specialty slug→UUID.

| العنصر             | الحالة                                | ملاحظة                                 |

**توصيات فريق العمل (محتوى)**

1. تنظيف DB ثم التحقق أن عدّاد «N طبيب» على `/team` = إنتاج فقط.
2. رفع `photo_url` و`slug` لكل استشاري ظاهر.
3. إن رغبت الإدارة بنشر أسماء القيادات: جدول CMS/`staff_profiles` بدل النص الثابت، مع موافقة خصوصية.
4. إضافة تمريض/صيدلية/مراكز تميز كأقسام اختيارية لاحقًا.

## 7. خلاصة

المنصة وصلت لمرحلة **واجهة عامة قوية نسبيًا** مع قرار منتج واضح: **الحجز بعد التسجيل**. الفجوة ليست «شكل الموقع» بقدر ما هي **تشغيل الحجز الآمن + نظافة البيانات + إكمال فريق العمل ظاهرًا وتشغيليًا**.

بإغلاق بنود المرحلة أ ثم ب، يصبح مسار المريض قابلًا للإطلاق؛ المرحلة ج تحسّن الثقة البصرية والاتساق؛ المرحلة د تثبّت الجودة المستمرة.
